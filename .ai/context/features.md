| M9 | **Fixed source-video upload 500s + dependency-floor audit:** every part/hike upload was failing server-side with `multipart.exceptions.MultipartParseError: Did not find CR at end of boundary` — a `python-multipart` 0.0.9 boundary-parser bug that only surfaces on large multipart bodies, not the tiny `TestClient` uploads M1a's local verification used, so it shipped unnoticed. Root cause: `pyproject.toml` pinned it `^0.0.9`, and Poetry's caret on a `0.0.x` version locks to that exact patch — with no `poetry.lock` committed (deliberate, so every image build re-resolves to latest), every rebuild kept re-landing on the same broken `0.0.9`. Fixed the constraint (`>=0.0.32,<1.0`, the actual latest available today) and audited every other dependency for the same caret-on-`0.x` trap (`fastapi`, `uvicorn`, `httpx` were minor-locked the same way; `pillow`/`sse-starlette`/`pytest` were major-capped below latest) — see `01-project-overview.md` "Dependency versioning". Also removed `aiofiles` (declared, never imported anywhere) and bumped the `htmx` CDN pin (`2.0.3`→`2.0.10`). Separately, the upload `<form>`s had zero progress/error UI (`hx-swap="none"`, no listener) — indistinguishable from "broken" even once uploads succeed, since a multi-GB file over a home connection can take a long time with no feedback at all; replaced both forms with `XMLHttpRequest`-based uploads showing live byte progress and surfacing any HTTP error inline (`templates/project.html`). **Verified live**: reproduced the exact `MultipartParseError` in `sdh`'s live container logs before the fix, then — after the user deployed `v0.4.1` — confirmed via the same container logs that it's gone; uploads now fail differently (a Traefik 60s proxy timeout, unrelated, see the Host migration roadmap row and M10) rather than 500ing before a byte is written. |
| M10 | **Fixed QSV hardware encode never actually engaging on `sdh`** (`Dockerfile`): `/health` reported `libx264` despite `/dev/dri` being correctly passed through — `gpu_detector.py`'s `h264_qsv` test-encode was silently failing every time. Root-caused live on `sdh`: the host's single GPU is a discrete Intel Arc A380 (DG2 — `lspci` shows no separate integrated GPU on this box); VAAPI/the `iHD` driver load fine, but ffmpeg's actual QSV encoder needs a further layer on top — the oneVPL GPU runtime, Debian package `libmfx-gen1.2` — which the image never installed (only `va-driver-all`, the VAAPI layer itself). Jellyfin on the same host was unaffected because it bundles its own self-contained `jellyfin-ffmpeg` build. Confirmed as the real fix by installing `libmfx-gen1.2` live in the running container (ephemeral, not persisted — gone on next recreate) and re-running the exact failing test-encode: clean exit. Added `libmfx-gen1.2` to `Dockerfile`'s apt install list for good. **Deployed and confirmed live 2026-08-20** — `sdh` runs `v0.4.3`, `/health`'s `encoder` field reads `h264_qsv`, and a real Summary+shorts build's container logs show every re-encode using `-c:v h264_qsv` (the concat and full-flight-with-music steps are `-c copy` by design, so they never touch the encoder). |
| M11 | **Chunked, resumable source upload** (`core/chunked_upload.py`): the single-request whole-file multipart upload (M1a/M9) hit a hard wall on `sdh` — Traefik's `websecure`/`web` entrypoints default `respondingTimeouts.readTimeout` to **30 minutes** (confirmed via Traefik's own `/api/entrypoints`, and via a live 8 GB upload that died at exactly `1800.000087s`, `502` + `readfrom ... i/o timeout`), and the user wants that global default left alone rather than raised (it's a sane cap for the other services behind the same proxy). So VidFactory now works around it instead of depending on infra: the client splits the file into 8 MiB chunks (`POST .../upload/begin` → `PUT .../upload/chunk?filename=&offset=`, repeated → `POST .../upload/finish`), each a fast, independent request nowhere near 30 minutes. Resumability is a side effect of the design, not extra work: there's no in-memory session state at all — `begin` just reports the current size of the staging file on disk, so a laptop sleep, network drop, or even a container restart mid-upload only costs the bytes since the last chunk; re-clicking Upload with the same file picks up from the real on-disk offset. A `409 {"offset": actual}` on `chunk`/`finish` handles a chunk that partially landed before a disconnect — client resyncs rather than getting stuck. Old whole-file `POST .../parts/upload`/`.../hike/upload` endpoints and the M9 XHR-progress handler were deleted outright, not kept alongside (`04-constraints.md`: no compat shims). **Verified**: `tests/backend/test_chunked_upload.py` covers begin→chunk→chunk→finish, resume returning a nonzero offset, and the offset-mismatch 409 path — but per `06-testing-conventions.md`'s in-memory-SQLite/`TestClient` limits (no real multi-GB transfer, no real Traefik in front), the only real proof is one full 8-10 GB upload against `sdh` after this deploys, watched via the staging file's size growing — exactly the gap that let the M9 multipart bug ship unnoticed in the first place. Not yet deployed. |

## Host setup (Fedora `xpsex`) — STALE, host retired

> `xpsex` is no longer available (home network/host changed after a move). Kept below only as a
> record of the quirks that applied to it; do not deploy against it. The next deploy target is a
> new host (55 TB storage, not yet detailed here) — see the "Host migration" roadmap item above.
- **Mount the `pg` SMB share** at `/mnt/pg` (NAS exports only `/volume1/backup` over NFS; `pg` is
  SMB-only, so it needs CIFS credentials). Until mounted, `/data/{InstaOut,Music,Summaries,Shorts}`
  are missing and `/health` reports `degraded` (still HTTP 200; the app stays reachable). `Archive`
  works because the app creates it on local disk.
- **NVIDIA NVENC — host-side fragile in two distinct ways:**
  1. After a **driver update** the CDI spec goes stale; regenerate it:
     `sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml`.
  2. After a **plain reboot** the `nvidia_uvm` module loads lazily, so `/dev/nvidia-uvm` is missing and
     the container fails to start with `CDI device injection failed … "/dev/nvidia-uvm": no such file or
     directory` — even though `nvidia-smi` works (base modules loaded, UVM not). Fix:
     `sudo modprobe nvidia_uvm && sudo nvidia-modprobe -u -c=0` (then regenerate the CDI spec).
  Dev compose uses the CDI device `nvidia.com/gpu=all`; the app selects `h264_nvenc`.
